# 鴻萊興業 V2 人工詢價與 Windows 預覽 MVP 設計

日期：2026-11-04  
目標期限：2026-11-25

## 目標與邊界

本輪把既有 `/order` 瀏覽器草稿原型擴充為可提交至 `honglai-v2-staging` 的 B2B／B2C 人工詢價流程，並提供 Windows 一鍵開啟本機 HTTP 開發預覽的方式。

本輪不建立自動估價、正式訂單、工作單、會員、線上付款或正式網站部署。所有未確認價格的產品只建立人工詢價，不顯示推測金額。既有 Logo、15 項產品分類、價格資料、第一階段八張資料表、RLS、企業合作及樣品冊提交流程均須保留。

## 產品與表單模型

`catalog.ts` 的 15 個產品 slug 作為穩定產品 ID。新增集中式產品詢價映射，將每個產品 ID 對應至既有五種表單類型：書籍裝訂、菜單、證書夾、施工本、其他／不確定。

產品詳情頁沿用 `/order?product=<slug>`。下單頁讀取並驗證查詢參數，合法時自動選取實際產品及適用表單；無效或缺少參數時由使用者從完整 15 項產品清單選擇。切換表單類型時不刪除既有規格選項，只依產品顯示適用欄位。

送出資料同時保存實際產品 ID、產品名稱、表單類型、數量，以及當次可見規格的 JSON 快照。不可只保存五種概括類別。

## 資料庫

新增一個非破壞性 migration，建立：

- `manual_inquiries`：公開詢價編號、idempotency key、客戶類型、聯絡與配送快照、希望日期、檔案狀態、特殊需求、備註、狀態及建立時間。
- `manual_inquiry_items`：詢價主表外鍵、產品 ID、產品名稱快照、表單類型、數量及規格 JSON；MVP 前端一次提交一項，但資料層允許未來多項產品。
- `manual_inquiry_status_history`：每次狀態變更的前後狀態、時間與操作者。

主表以 UUID idempotency key 唯一限制防止重複建立。詢價編號另設唯一限制。資料庫函式在同一交易內建立主表、明細與初始 `pending_review` 歷史紀錄；重複 idempotency key 回傳原詢價編號，不新增第二筆。

三張表啟用 RLS。匿名瀏覽器不得直接讀寫；只有既有管理員角色可以查詢，狀態更新權限沿用第一階段管理員判斷。Edge Function 使用伺服器端 Secret Key 呼叫受限的資料庫函式，Secret 不進入瀏覽器或版本控制。

## Edge Function 與安全流程

新增 `submit-manual-inquiry`，沿用既有公開 Function 的 CORS／Origin、Publishable Key 驗證、伺服器 Supabase client、限流與錯誤格式。

處理順序：

1. 驗證 Origin 與 Publishable Key。
2. 解析並限制 JSON 大小。
3. 驗證 idempotency UUID、15 項產品 ID、允許的表單映射、客戶類型、姓名、電話、Email、數量、日期及字串長度。
4. 以雜湊來源識別執行既有限流。
5. 呼叫資料庫交易函式。
6. 僅在資料庫已存在完整主表、明細及初始歷史後回傳詢價編號。

網路錯誤或伺服器錯誤不得顯示成功。前端重試沿用同一 idempotency key；成功後才產生下一個 key。測試只使用明確標示的虛構資料。

## 前端互動

`/order` 保留目前四步驟與 localStorage 草稿。介面清楚分成：

- 儲存草稿：自動保存在目前瀏覽器，不代表送出。
- 正式送出人工詢價：呼叫 Edge Function；送出期間鎖定按鈕，成功顯示詢價編號，失敗顯示鴻萊尚未收到資料並保留草稿。

前端先做必要格式驗證，伺服器重做完整驗證。只有與產品相關且目前可見的欄位參與必填檢查；不適用欄位不得阻擋提交。Email、電話、正整數數量、希望日期及產品映射皆需驗證。

## Windows 一鍵預覽

在 `honglai-v2` 根目錄建立 `啟動網站預覽.bat`，預設啟動 `npm run dev` 並開啟本機網址。啟動前檢查指定連接埠：

- 若已是可回應的鴻萊預覽，直接開啟瀏覽器，不重複啟動或停止程序。
- 若連接埠被其他服務占用，顯示容易理解的錯誤並保留該程序。
- 若依賴或環境設定缺少，顯示修復提示，不安裝 Docker，也不把任何金鑰寫入批次檔。

正式建置仍使用 Next.js 靜態匯出。`npm run build` 必須產生 `out/index.html`，並透過本機 HTTP 靜態伺服器驗證 HTML、CSS、JavaScript、Logo、產品頁與表單資源。

README 記錄開發預覽、關閉方式、staging 辨識、正式建置、靜態預覽、`out/index.html` 位置與常見錯誤。

## 驗證與完成條件

本機驗證包括 ESLint、TypeScript no-emit、production build、靜態匯出檔案檢查、15 項產品映射測試、前端驗證及既有企業合作／樣品冊回歸檢查。

staging 驗證包括 migration 相容性、Edge Function 部署，以及虛構 B2B、B2C、相同 idempotency key 重送、驗證失敗與錯誤回應測試。完成報告必須區分已由資料庫確認的結果、僅本機通過的結果與任何因權限或環境受阻而未驗證的項目。

不執行 git push、正式網站部署、破壞性 migration、資料刪除或正式客戶資料測試。

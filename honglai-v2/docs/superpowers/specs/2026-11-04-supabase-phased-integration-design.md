# 鴻萊興業 V2 Supabase 分階段串接設計

## 已核准流程

### 訂單與工作單

1. 客戶選擇產品與規格。
2. 系統只使用已確認且完整的價格規則重新計價。
3. 客戶確認金額並提交訂單。
4. 系統在同一個資料庫 transaction 建立訂單編號、訂單與價格快照。
5. 系統同時建立唯一工作單，初始狀態為「待審核」。
6. 公司確認規格、設計檔案及交期後，才安排正式製作。

提交訂單不代表開始製作。一張訂單只對應一張工作單；工作單可包含多筆產品明細。不適用的製作欄位顯示「不適用」，不要求客戶虛填封面、材質或燙金資料。

### 價格安全邊界

- 只有來源、數量級距、選項、加工費及客群規則均已確認的品項，才能自動計價與下單。
- 任一必要資料未確認時，回傳人工詢價，不顯示推算金額。
- B2B、B2C 規則分開保存；新版本不覆寫歷史版本。
- 訂單保存產品、規格、價格版本與每一項金額的不可變快照。
- 不新增 Excel 或人工確認資料以外的價格、優惠、尺寸、材質或加工能力。

## 分期範圍

### 第一階段（本次本機程式碼）

- Supabase migration 基礎架構。
- Supabase Auth 管理員、經理與一般內部人員角色。
- 企業合作申請與狀態歷史。
- 材質樣品冊申請與狀態歷史。
- Edge Functions 驗證、來源限制、速率限制及重複提交防護。
- 靜態 Next.js 表單呼叫 Edge Functions。

不包含合作廠商登入、產品價格、正式訂單、Storage 上傳、工作單或付款。

### 第二階段

- 產品、規格選項、價格版本及來源追蹤。
- B2B／B2C 規則、人工詢價條件及伺服器端重新計價。
- 只有 confirmed 規則可啟用自動計價。

### 第三階段

- 正式訂單及不可變價格快照。
- 私有設計檔案上傳及失敗補償流程。
- 訂單與待審核工作單在同一 transaction 建立。
- 工作單明細、進度、負責人及完整修改歷史。

## 第一階段資料流

1. 使用者在既有靜態頁面填表。
2. 前端完成基本格式驗證並產生 idempotency UUID。
3. 表單呼叫公開 Edge Function；瀏覽器只帶 Publishable Key。
4. Edge Function 驗證 Origin、欄位、同意狀態與長度。
5. Edge Function 使用加鹽 SHA-256 指紋呼叫資料庫速率限制函式。
6. Edge Function 使用只存在伺服器端的 Secret Key 寫入申請。
7. 資料庫 unique constraint 防止相同 idempotency UUID 建立兩筆資料。
8. 前端只有在取得正式申請編號後才顯示已收到。

## 權限設計

- `anon`：沒有業務資料表的直接讀寫權。
- `authenticated`：預設仍無權限；必須存在啟用中的 `profiles` 及 `user_roles`。
- `staff`：唯讀企業合作與樣品冊申請。
- `manager`、`admin`：讀取並更新申請狀態、處理人及內部備註。
- Edge Functions：使用 Secret Key 寫入，但必須先完成應用層驗證。
- 角色資料目前由專案擁有者以 Dashboard SQL 手動建立，前台沒有角色授權介面。

## 錯誤與一致性

- Edge Function 或資料庫失敗：前端明確顯示「尚未收到」，不顯示成功。
- 網路重試：沿用同一 idempotency UUID，若前一次其實已完成則回傳同一申請編號。
- 狀態變更：資料庫 trigger 自動寫入歷史表。
- 第一階段不包含檔案上傳，因此沒有半完成的附件狀態。
- 第三階段必須先完成檔案暫存，再於單一 transaction 建立訂單與工作單；失敗時不產生半張訂單，孤立暫存檔由排程清理。

## 部署邊界

本機檔案完成不代表已部署。未經使用者再次確認，不執行以下操作：

- `supabase link`
- `supabase db push`
- `supabase functions deploy`
- 建立正式 Auth 使用者、資料表、bucket 或 Secret
- 修改正式網站環境變數或重新部署網站

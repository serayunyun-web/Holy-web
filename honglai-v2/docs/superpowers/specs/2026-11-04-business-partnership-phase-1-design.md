# 鴻萊興業 V2｜企業合作功能第一階段設計

狀態：待使用者審查
範圍：純前端介面與驗證，不建立後端、資料庫、正式上傳或管理員系統

## 1. 目標與邊界

第一階段重整既有企業合作內容，建立未來串接 Supabase 所需的公開頁面與表單介面，同時保留現有首頁、產品、估價、FAQ、聯絡、訂單、導覽列、頁尾與原始公司 LOGO。

本階段不會：

- 修改 `output: "export"` 或現有靜態部署架構。
- 建立 Supabase 專案、資料表、Storage bucket、Auth 使用者或外部雲端資源。
- 建立 API、正式資料提交、持久化儲存、附件上傳、管理後台或合作廠商登入。
- 顯示提交成功、洽詢編號，或暗示鴻萊已收到資料。
- 修改既有價格表、估價公式、訂單草稿格式或商業規則。
- 宣稱合作折扣、免費打樣、免費樣品冊、免運、最低訂購量或交期保證。

## 2. 路由與頁面架構

### `/business`

保留現有導覽列入口，重整為企業合作主頁：

1. 主視覺 Banner
2. 數位燙金皮革封面與半成品加工主打服務
3. 三大合作模式
4. 合作對象
5. 合作優勢
6. 五步驟合作流程
7. 企業合作洽詢表單
8. 材質樣品冊與合作廠商專區入口

### `/business/sample-request`

材質樣品冊介紹與申請表單介面。頁面明確說明申請不等於核准，樣品內容、費用、運費與寄送方式皆須由專人確認。

### `/partners`

合作廠商專區介紹頁。第一階段只提供資格說明、未來功能預告與申請入口，不提供登入或受保護資料。申請入口導向 `/business` 的企業合作洽詢表單，並預先選擇「其他合作需求」。

## 3. 企業合作主頁

### 主視覺

- 英文小標：`BUSINESS PARTNERSHIP`
- 主標題：`專業印後加工，成為你的製作夥伴`
- 使用核准的副標題。
- 「了解合作服務」捲動至主打服務。
- 「洽詢企業合作」捲動至表單。

### 主打服務

以數位燙金皮革封面半成品為主角，說明鴻萊先完成皮革封面的數位燙金加工，再交由合作店家自行完成後續裝訂。圖片使用與現有網站一致的非寫實佔位圖，清楚標示為待替換素材。

特色只包含已確認內容：單本及少量客製、數位燙金皮革封面、半成品合作、合作店家可自行完成後續裝訂，以及跨縣市寄送合作。

### 三大合作模式

- 半成品加工合作
- 完整裝訂代工
- 特殊加工與客製合作

每張卡片的「洽詢此服務」會捲動至企業表單並預先帶入對應合作類型。特殊加工文案會保留「由專人評估，不保證所有規格均可承接」。

### 合作對象與合作優勢

合作對象使用簡潔文字圖示，不描述為既有客戶。合作優勢只呈現需求文件列出的六項內容，不新增價格、數量或交期承諾。

### 合作流程

桌面採五步驟橫向排列，手機改為直向流程：

1. 提出合作需求
2. 確認規格與報價
3. 確認合作內容
4. 安排加工製作
5. 完成交付

## 4. 表單介面與驗證

### 共用原則

企業洽詢與樣品冊申請各自保存獨立的 React state，不使用 localStorage 冒充正式儲存。兩張表單可共用欄位元件、驗證工具與狀態訊息，但不混合資料型別。

按鈕名稱使用「檢查填寫內容」，不使用「送出」或「提交」。驗證通過後只顯示：

> 內容格式檢查完成，但尚未傳送給鴻萊。正式提交功能將於後續階段開放。

表單頁面固定顯示「尚未開放正式提交」。不產生洽詢編號，也不清空使用者已填內容。

### 企業合作洽詢表單

欄位包含：

- 公司／店家名稱（必填）
- 聯絡人（必填）
- 聯絡電話（必填）
- Email（必填）
- LINE ID
- 所在縣市（必填）
- 合作類型（必填）
- 需求產品
- 預估數量
- 尺寸規格
- 材質需求
- 希望交期
- 需求說明（必填）
- 參考檔案區

合作類型固定為半成品加工、完整裝訂代工、特殊加工與客製、其他合作需求。

參考檔案區在第一階段停用，只說明正式上傳尚未開放。檔案類型、大小與數量限制列為第二階段待確認，不提供可選取檔案的控制項。

### 樣品冊申請表單

欄位包含公司／店家名稱、聯絡人、電話、Email、所在縣市、有興趣的材質或加工項目、申請用途與備註。第一階段只驗證內容，不收集完整寄送地址。

### 驗證規則

- 必填欄位需有非空白內容。
- Email 使用合理格式檢查。
- 電話只接受常見電話字元，並要求足夠的數字位數。
- 預估數量如有填寫，必須是大於零的整數。
- 希望交期如有填寫，必須是有效日期。
- 錯誤訊息與欄位建立 `aria-describedby` 關聯。
- 驗證失敗後將焦點移至第一個錯誤欄位。
- 表單支援鍵盤操作，互動元素具可見焦點樣式。

只有在新頁面需要新增明確入口時才調整既有頁面；不改動 Header 的「企業合作」路由，也不新增尚未可用的登入導覽。

## 6. 視覺與響應式設計

沿用現有青綠、米白、暖棕色票、Noto Serif TC／Noto Sans TC、圓角卡片、淺色邊框與輕微陰影。主打區的視覺語彙取自皮革封面、燙金壓印與裝訂樣張，但使用抽象 CSS 佔位圖，不生成或暗示真實公司作品。

- 桌面：主打區雙欄，合作模式三欄，流程橫向五步。
- 平板：主打區與卡片依可用寬度改為兩欄或單欄。
- 手機：所有內容單欄，流程直向，表單控制項滿版，不產生頁面橫向捲動。
- 尊重 `prefers-reduced-motion`；動態效果限於既有 Hover 與短距離轉場。

## 7. 第二階段 Supabase 邊界

第一階段完成後另行提供 Supabase 設定清單，內容包括：

- 專案與環境變數規劃。
- `business_inquiries`、`sample_requests`、`partners` 的資料表與 migration。
- Supabase Auth 管理員驗證及角色／RLS 策略。
- Storage bucket、檔案類型、大小、數量與私有存取策略。
- 後端驗證、重複提交防護、濫用防護與錯誤處理。
- 靜態部署轉為支援伺服器端 API 的遷移方案。

上述項目在使用者再次核准前不實作。

## 8. 驗收與測試

第一階段需通過：

- ESLint。
- TypeScript `--noEmit`。
- Next.js 靜態建置。
- `/business`、`/business/sample-request`、`/partners` 路由生成。
- 三張合作卡片能正確預填合作類型並捲動至表單。
- 兩張表單的必填、Email、電話、數量及日期驗證。
- 驗證通過後仍明確顯示未傳送。
- 不存在正式提交 API、附件上傳或 localStorage 正式儲存。
- Header、Footer、LOGO、產品頁、估價頁、FAQ、聯絡頁與訂單頁未被破壞。
- 桌面、平板與手機版面無文字溢出、重疊或頁面橫向捲動。

## 9. 待公司確認項目

以下保留至第二階段：

- Supabase 專案擁有者、環境與部署位置。
- 管理員帳號建立與角色管理流程。
- 附件允許格式、單檔大小、總數與保留期限。
- 個資告知的正式公司版本、保存期限與聯絡窗口。
- 防濫用策略及是否採 CAPTCHA。
- 樣品冊費用、運費、申請資格、可提供內容及寄送方式。
- 合作廠商核准標準及後續專區權限。
